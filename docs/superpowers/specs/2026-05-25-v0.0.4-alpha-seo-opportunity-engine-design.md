# v0.0.4-alpha SEO Opportunity Engine Design

PRD source: [PRD_v0.0.4-alpha.md](file:///Users/philipclaw/Downloads/TraeSolo/PilatesProject/NewCareers/PRD_v0.0.4-alpha.md) (document header shows “v0.0.4-beta.1”; treat it as the current v0.0.4-alpha target scope)

Baseline: v0.0.3 (generator + evaluation + optimization copilot loop)

## Scope

Upgrade the optimization loop from “missing keywords + basic image quality” to an LLM-driven SEO Opportunity Engine that reasons:

- WHY SEO is low (weakness analysis)
- WHAT is missing (search intent / feature / customer intent expansion)
- WHAT to add (injectable terms)
- EXPECTED impact (estimated SEO gain)
- VERIFY improvement (delta after regeneration)

## Hard Constraints (Approved)

- No new endpoint. Continue using `POST /api/generate`.
- Allowed: backend adds new fields, new agents, and additional LLM calls.
- Strict failure: if any new v0.0.4 agent fails, the whole `/api/generate` request fails.
- “Do NOT relax SEO evaluator”: evaluation logic must not be tuned to inflate SEO. Improvements must come from better information/coverage/generation.
- Progress UX: frontend uses pseudo-progress (stage messages + timer), not streaming/SSE.

## Non-Goals

- No evaluator manipulation.
- No streaming responses in this iteration.
- No cross-session persistence of SEO history (only in-page state like v0.0.3 delta).
- No new marketplace support.

## Current Architecture (v0.0.3)

- Existing pipeline produces:
  - listing result (title/bullets/description/keywords)
  - explainable evaluation (overall + dimensions + suggestions)
  - `seo_opportunity` (missing keywords + recommended placement)
  - v0.0.3-beta fields: `optimization`, `image_quality`, `delta` (delta is frontend computed)
- Existing reliability:
  - DashScope timeout + retry wrapper
  - strict mode support + `_debug.calls[]` with requestId tracing

## Target Architecture (v0.0.4-alpha)

### Pipeline placement

Append the v0.0.4 SEO engine after listing generation + evaluation are available:

Generate listing → Evaluation (unchanged) → Existing gap signals (seo_opportunity, etc.) → v0.0.4 SEO Engine agents → return response

### New LLM Agents (multi-call, aligned to PRD FR-022~FR-026)

All agents must:

- use DashScope text JSON call wrapper (same reliability/timeout/retry)
- write `_debug.calls[]` record with:
  - agent name
  - status
  - requestId
  - attempts
  - error (if any)
- in strict mode: throw immediately on error, aborting the entire request

Agents:

1) **FR-022 SEO Weakness Analysis Agent**
   - Input: listing + evaluation + keyword intelligence + `seo_opportunity` + `vision_context`
   - Output:
     - `weakness[]`: `{ type, severity, reason }`
   - Weakness types: `primary_keyword`, `feature_coverage`, `customer_intent`, `usage_scenario`, `search_intent`
   - Severity: `critical | high | medium | low`

2) **FR-023 Search Intent Expansion Agent**
   - Input: product context + weakness summary
   - Output:
     - `search_intent[]`: string list

3) **FR-024 Feature Expansion Agent**
   - Input: seller input features + listing summary + weakness summary
   - Output:
     - `feature_expand[]`: string list

4) **FR-025 Customer Intent Expansion Agent**
   - Input: vision context + seller input + weakness summary
   - Output:
     - `customer[]`: string list

5) **FR-026 SEO Opportunity Ranking Engine**
   - Input: weakness + expansions + missing keywords + evaluation
   - Output:
     - `opportunity[]`: ranked list
       - `{ type, keyword, estimated_gain, priority }`
   - Type weighting (PRD):
     - primary keyword: 10
     - search intent: 8
     - feature expansion: 6
     - customer expansion: 5
     - long tail keyword: 4
   - Rule: ranking must be consistent with the weight guidance; LLM can estimate gain but we should add a lightweight sanity check (e.g. priority order agrees with weight tiers when estimated gains are close).

### New Response Fields (additive, backward compatible)

Keep existing fields and add a new top-level field:

- `seo_engine?: { weakness: Weakness[]; search_intent: string[]; feature_expand: string[]; customer: string[]; opportunity: RankedOpportunity[] }`

Do not remove:

- `seo_opportunity` (v0.0.3 missing keywords)
- `optimization` / `image_quality` / `delta`

## Apply Layer (FR-027)

Frontend-only, still no backend call on Apply.

### Injection target (current decision)

Inject into Product Input: Key Features (`featuresText`), one per line.

### Format convention (to support v0.4 multi-type opportunities)

To keep injected items self-descriptive without changing backend contract, prefix the injected lines:

- `[SEO:Primary Keyword] <term>`
- `[SEO:Search Intent] <term>`
- `[SEO:Feature] <term>`
- `[SEO:Customer] <term>`

De-duplication should be case-insensitive on the whole normalized line (trim + collapse whitespace).

## Saturation / Continue (FR-028)

v0.0.4 PRD describes using SEO score history + expected gain.

v0.0.4-alpha MVP approach (no persistence):

- Keep the existing v0.0.3-beta “continue decision” concept, but compute it from:
  - current SEO dimension score (from evaluation)
  - top ranked opportunity’s `estimated_gain`
- Rule: if `estimated_gain < 3` then `continue=false` with reason “SEO opportunity exhausted”
- History is only tracked on frontend for delta display; no backend persistence.

## Frontend Progress UX (Pseudo Progress, Approved)

Goal: manage user patience under multi-agent LLM latency while preserving a single request/response API.

### Behavior

- When Generate starts, show a step-based progress UI with a timer-driven pseudo progression.
- Stages (example; aligned to actual pipeline order but not guaranteed real-time):
  1. Generating listing
  2. Evaluating
  3. SEO weakness analysis
  4. Search intent expansion
  5. Feature & customer expansion
  6. Ranking opportunities
  7. Finalizing response
- The UI advances every N seconds, clamps at the last stage until response returns.
- If elapsed time exceeds a threshold (e.g. 20s), show a patience hint (e.g. “Model calls may take longer; still working”).

### Constraints

- No streaming. This is not a promise of exact backend progress.
- Debug drawer remains the source of truth for requestId/attempts per agent.

## Error Handling & Strict Mode

- Strict mode behavior (approved): if any new v0.0.4 agent fails, return 500.
- Error response must include `_debug` with:
  - all completed calls
  - the failing agent call record with `status:"error"`, `requestId` if available, and message.
- Frontend displays the error banner and keeps Debug drawer available.

## Acceptance Criteria

- AC-001: Each v0.0.4 agent produces JSON matching its schema.
- AC-002: `_debug.calls[]` shows every new agent with requestId and attempts.
- AC-003: If any v0.0.4 agent fails, `/api/generate` fails (500) and user can see which agent failed via Debug.
- AC-004: Frontend shows pseudo progress stages during Generate.
- AC-005: SEO improvement comes from regenerated output; evaluation logic is unchanged.
- AC-006: Apply injects a ranked opportunity into Key Features with a type prefix, and a subsequent Generate can reflect the injected term.

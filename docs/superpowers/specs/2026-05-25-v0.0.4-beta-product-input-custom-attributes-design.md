# v0.0.4-beta Product Input Custom Attributes Design

Baseline: v0.0.4-alpha.1 (deployed to Vercel, released on GitHub)

Goal: improve Product Input flexibility for diverse products while preserving v0.0.4-alpha.1 capabilities, and ensure custom attributes participate in listing generation (no “UI-only” fields).

## Scope (Approved)

### Keep unchanged

- Images: upload 1–5, existing validation, and vision understanding in pipeline.
- Existing optimization loop: Apply → Generate again → Delta compare.
- SEO Opportunity Engine (FR-022~FR-028) and its strict failure behavior.
- Debug traceability: `_debug.calls[]` + requestId visibility (debug drawer).
- Loading UX: stage indicator.
- No new endpoint. Continue using `POST /api/generate` with multipart/form-data.
- Marketplace support remains unchanged (currently `US` only).

### Change (v0.0.4-beta)

- Product Input text fields are refactored:
  - Keep `Product Name` (required).
  - Keep `Key Features` (required, one per line).
  - Remove fixed fields: `Material`, `Brand`, `Color`, `Dimensions`.
  - Add a new optional module: `Product Attributes` (custom Key-Value table) with CRUD.
  - Keep `marketplace` and `Target Audience (optional)` unchanged.
- Custom attributes must be consumed by backend generation as first-class context.

## UX Requirements (High Priority)

### Visual efficiency

- Reduce pointer travel by co-locating high-frequency actions:
  - `+ Add Attribute` near module header.
  - Row-level `Delete` button aligned at far right of that row.
  - `Generate` remains easy to reach (prefer sticky bottom within Product Input column on desktop).
- Provide “quick add” chips/buttons to create common keys (but not fixed schema):
  - Suggested chips: `+ Material`, `+ Brand`, `+ Color`, `+ Dimensions`.
  - Clicking a chip inserts a new attribute row with the key prefilled; the user can still edit or delete it.

### Product Attributes (Key-Value table)

Each row:

- `key`: string (required for the row to be considered valid)
- `type`: enum
  - Supported types (approved): `text` | `multiline` | `select`
- `value`: string

Row behavior:

- Add: append a new empty row.
- Edit: inline editing.
- Delete: removes the row.

Validation:

- Attributes are optional overall.
- Within attributes:
  - Rows with empty `key` are ignored on submit (do not send to backend).
  - Rows with `key` but empty `value` are allowed but discouraged; UI can show a subtle warning.

### Select type (Approved option B: templates only)

No per-row user-defined options editor.

Implementation:

- Provide template dropdowns that can be applied to generate a select-type row:
  - `Size`: S/M/L/XL
  - `Color`: Black/White/Gray/Blue/Red
  - `Voltage`: 110V/220V
  - `Wattage`: 30W/60W/100W
  - `Capacity`: Small/Medium/Large
- For `select` rows, the UI presents:
  - `key` (prefilled by template, editable)
  - `value` (dropdown bound to the template’s option list)
- Backend receives only the selected `value` (not the entire option set), because option set is UI convenience.

## Backend Contract (No new endpoint)

### Transport: multipart/form-data additions

Add a new form field:

- `custom_attributes`: JSON string

Schema:

```ts
type CustomAttributeType = "text" | "multiline" | "select"

type CustomAttribute = {
  key: string
  type: CustomAttributeType
  value: string
}
```

### Server-side request type

Extend `GenerateRequest` with an additive optional field:

```ts
custom_attributes?: CustomAttribute[]
```

Backward compatibility:

- If `custom_attributes` is missing or invalid JSON:
  - Treat as `undefined` (non-fatal).
  - In strict mode, do not fail the whole request because of attribute parsing; only fail for required baseline fields.

## Pipeline Integration (Attributes must affect generation)

### Principle

Attributes are independent from Key Features:

- Do NOT automatically merge attributes into Key Features in frontend.
- Do NOT “fake” usage by appending attribute text into features without structure.

### Prompt integration strategy (Recommended)

When generating the listing, include a dedicated, structured section:

```
Product Attributes (seller provided):
- <key>: <value>
- <key>: <value>
```

Agent wiring:

- Extend the existing generator prompt builder (where seller input is currently summarized) to incorporate `custom_attributes` if present.
- Ensure downstream SEO engine agents can also “see” this information by including it in the shared context summary passed to those agents (without changing their fundamental logic).

## UI Architecture / Components

### Components (planned)

- `ProductForm`:
  - Replace removed fixed fields with a `ProductAttributesEditor`.
- `ProductAttributesEditor`:
  - Local editing UI for `customAttributes[]`.
  - Quick-add chips and template actions.

### State

`ProductFormValue` extends with:

```ts
customAttributes: CustomAttribute[]
```

### Submit payload

On submit:

- Serialize filtered rows (`key.trim().length > 0`) to JSON.
- `form.append("custom_attributes", JSON.stringify(rows))`

## Non-Goals

- No new marketplace support.
- No cross-session persistence of attributes beyond current page state.
- No per-row custom select option editor (templates only).
- No refactor of SEO evaluator logic.

## Acceptance Criteria

- AC-001: Product Input shows Product Name + Key Features (required) + Product Attributes (optional) + marketplace + target audience.
- AC-002: User can add/edit/delete attribute rows and use quick-add chips.
- AC-003: Select templates create a select-type row and allow choosing a value without manual option editing.
- AC-004: Backend receives `custom_attributes` and listing generation output demonstrably changes when attributes change (same other inputs).
- AC-005: No other v0.0.4-alpha.1 feature is removed or behavior-changed (except the removed fixed fields and any minimal prompt wiring necessary to include attributes).
- AC-006: Publish as `v0.0.4-beta` to GitHub and Vercel updates via Git integration.

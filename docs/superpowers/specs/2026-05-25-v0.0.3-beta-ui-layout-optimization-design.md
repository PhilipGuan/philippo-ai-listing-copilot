# v0.0.3-beta UI Layout & Guidance Optimization Design

PRD baseline: [PRD_v0.0.3-beta.md](file:///Users/philipclaw/Downloads/TraeSolo/PilatesProject/NewCareers/PRD_v0.0.3-beta.md)

Scope: Improve frontend layout + guidance efficiency so sellers can apply optimization suggestions and trigger the next generation faster.

Hard constraint: This iteration MUST NOT change v0.0.3 generation logic (pipeline order, LLM calls, backend behavior). Frontend-only UI/UX changes.

## Goals

- Make the three core concepts visually independent and simultaneously visible on desktop:
  - Product Input
  - Optimization Opportunity
  - Generated Listing
- Reduce confusion between recommendation “position” (Title/Bullets/Description) and available input fields.
- Improve iteration speed: Apply → input updates → Generate again → see delta.
- Keep debug access available but not occupying primary layout.

## Non-Goals

- Do not change backend API contract beyond what v0.0.3-beta.1 already outputs.
- Do not change agent/pipeline behavior, prompts, or model selection.
- Do not introduce new endpoints.
- Do not implement resizable splitters in this iteration.

## UX Decisions (Approved)

- Desktop layout: 3 columns (left → right): Product Input / Optimization / Listing.
- Each column has its own scroll container (prevents overall page from becoming extremely tall).
- Mobile/compact layout: vertical stacking (Input → Optimization → Listing).
- Debug access: floating button at bottom-right opens a right-side drawer.
- Recommendation copy: show “Impact area” and “Apply target” separately:
  - Impact area: Title / Bullets / Description (where it improves the generated output)
  - Apply target: Key Features (the concrete input field updated by Apply in this version)

## Layout Spec

### Desktop (≥ lg)

- Overall: keep the existing header at top.
- Main content becomes a 3-column grid:
  - Column 1: Product Input panel (existing ProductForm)
  - Column 2: Optimization panel (existing OptimizationPanel)
  - Column 3: Listing panel (existing ResultPanel)
- Height model:
  - On desktop, the page itself should not scroll (or nearly not scroll). Lock the main page container with `overflow-hidden` (desktop only) and let columns scroll internally.
  - The 3-column region uses a fixed “viewport height” container (e.g. `calc(100vh - headerHeight - footerHeight - pagePadding)`).
  - Each column is a scroll container with:
    - `overflow: auto`
    - `overscroll-behavior: contain` (avoid scroll chaining)
    - consistent padding + rounded border styling consistent with current UI.

### Mobile (< lg)

- Stack panels vertically in this order:
  - Product Input
  - Optimization
  - Generated Listing
- Default behavior can be normal page scroll; if nested-scroll feels acceptable, columns can keep internal scroll. Prefer simplest (page scroll) unless content becomes too tall.

## Recommendation Copy + Apply Mapping

Problem: current recommendation text like “Recommendation: add to Title” can confuse because the seller cannot directly edit Title in the input panel.

Solution: every keyword opportunity card shows two distinct lines:

- Impact: “Improves: Title / Bullets / Description”
- Apply: “Apply will add this keyword into: Key Features”

Apply behavior remains unchanged:

- Clicking Apply inserts the keyword into Key Features (new line, de-duplicated case-insensitively).
- Focus/scroll into the Key Features textarea.
- Seller clicks Generate again (no backend call on Apply).

## Applied Suggestion Visibility (Effectiveness-Based)

Goal: avoid repeating already-applied suggestions while still supporting a continuous optimization loop.

Core principle: hiding is based on whether the applied change is reflected in the latest generated result, not whether the user clicked Apply historically.

Frontend state:

- Maintain an in-session `appliedKeywords` set (does not persist across refresh).
- When user clicks Apply:
  - insert keyword into Key Features (existing behavior)
  - record the keyword into `appliedKeywords`

Rendering rule for keyword opportunities:

- If a keyword was applied before AND it is no longer detected as missing in the current run, it will naturally disappear because backend output `optimization.keyword` is derived from missing keywords.
- If a keyword was applied before BUT it is still detected as missing in the current run, it should still be shown (user can Apply again), and the UI should mark it as “Applied before (still missing)”.

This preserves the optimization loop:

Apply → input changes → Generate → evaluation/missing keywords re-evaluated → show remaining opportunities → Apply again.

## Debug Drawer (Minimal)

- Floating button: bottom-right, visible when `debugInfo` exists.
- Click opens a right-side drawer (overlay + panel):
  - Title: Debug
  - Content: formatted JSON (`JSON.stringify(debugInfo, null, 2)`)
  - Actions: Copy JSON
  - Close: ESC, overlay click, and close button.
- No filtering/search in this iteration.

## Acceptance Criteria

- Desktop:
  - Three panels visible side-by-side.
  - Each panel scrolls independently without expanding the whole page.
- Mobile:
  - Panels stack vertically in correct order and remain usable.
